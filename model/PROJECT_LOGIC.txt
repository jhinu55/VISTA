# VISTA - Vehicle Intelligence System for Telematics & Analytics

## High-Level Architecture

**Type:** Full-stack vehicle health monitoring application with ML-powered predictive maintenance
**Stack:** Next.js 15 (App Router) + React 19 + TypeScript 5 | Python 3.x ML backend
**Pattern:** API-driven architecture with Python ML model generating predictions consumed by React frontend

---

## Machine Learning Model - Core Logic

### File: `model/data_analysis_agent.py`

**Purpose:** Analyzes vehicle sensor telemetry data to detect anomalies and predict maintenance needs

**Three-Tier Anomaly Detection Algorithm:**

1. **Threshold-Based Detection** (`detect_threshold_anomalies()`)
   - Checks if sensor values exceed safe operational ranges
   - Predefined thresholds for 6 sensors:
     - Coolant Temperature (cTemp): 70-110°C
     - Engine RPM: 500-6500
     - Vehicle Speed: 0-200 km/h
     - Engine Load (eLoad): 10-90%
     - Mass Air Flow (maf): 2-15 g/s
     - Battery Voltage: 11.5-14.5V
   - Logic: `if value < min_threshold → WARNING/HIGH severity` | `if value > max_threshold → HIGH/CRITICAL severity`

2. **Rate-of-Change Detection** (`detect_rate_of_change()`)
   - Detects rapid fluctuations between consecutive sensor readings
   - RoC thresholds:
     - RPM: 1500 change per reading
     - Speed: 30 km/h change per reading
     - Coolant Temp: 15°C change per reading
   - Logic: `|current_value - previous_value| > threshold → WARNING`
   - Prevents false positives by checking device continuity between readings

3. **Pattern-Based Detection** (`detect_patterns()`)
   - Multi-sensor correlation analysis for complex failure modes:
     - **Alternator Failure:** `battery < 12.5V AND rpm > 2000` → Battery not charging despite engine running
     - **Transmission Slip:** `rpm > 4000 AND speed < 60` → High revs with low actual speed
     - **Engine Overload:** `eLoad > 80% AND maf < 3 g/s` → Excessive load with insufficient air intake

**Alert Aggregation Logic** (`process_anomalies()`)
- Time-windowed alert clustering (120-second windows)
- Prevents alert flooding by grouping anomalies from same time period
- Tracks min/max sensor values within each window
- Severity escalation: Takes highest severity from aggregated anomalies
- Data structure per alert:
  ```python
  {
    alert_id, device_id, 
    start_time, end_time,
    severity: 'INFO'|'WARNING'|'HIGH'|'CRITICAL',
    issues: ['THRESHOLD_cTemp', 'PATTERN_ALTERNATOR', ...],
    factors: ['cTemp', 'battery', ...],
    sensor_snapshot: {current sensor readings},
    min_values: {min readings in window},
    max_values: {max readings in window},
    anomaly_count: total_anomalies_in_window
  }
  ```

**Output:** JSON file (`detected_anomalies.json`) with array of alert objects

## Backend API - Data Bridge

### File: `src/app/api/predictions/route.ts`

**Purpose:** REST API endpoint bridging Python ML output to frontend

**Logic:**
- GET request handler
- Reads `detected_anomalies.json` from filesystem using Node.js `fs` module
- Returns JSON array of predictions
- Error handling with 500 status on file read failure

**Data Flow:** Python ML model → JSON file → Next.js API route → Frontend components

## Frontend Architecture - Key Logic Components

### Type System (`src/types/predictions.ts`)

Defines TypeScript interfaces matching Python ML output:
- `Prediction`: Complete alert object with sensor data, severity, issues array
- `Vehicle`: User's vehicle with deviceId mapping to ML model device_id

### Mock Data Layer (`src/lib/mockData.ts`)

**Critical Mapping Logic:**
- 4 demo vehicles with `deviceId` field that **must match** `device_id` in ML predictions
- Example: Toyota Camry → deviceId: 12 → matches predictions where device_id = 12
- Enables correlation: Frontend vehicle object ↔ ML model predictions
- Also contains mock appointment data for demo purposes

## State Management & Data Flow

### Dashboard Component (`src/components/client/ClientDashboard.tsx`)

**Core Logic:**
1. **Data Fetching:** `useEffect` → fetch `/api/predictions` → setState
2. **Alert Filtering Algorithm:**
   ```typescript
   predictions
     .filter(p => ['CRITICAL', 'HIGH'].includes(p.severity))  // Only urgent alerts
     .sort((a, b) => new Date(b.start_time) - new Date(a.start_time))  // Most recent first
     .slice(0, 3)  // Top 3 only for dashboard
   ```
3. **Vehicle Name Resolution:** Uses `mockVehicles.find(v => v.deviceId === prediction.device_id)` to map device IDs to human-readable vehicle names
4. **Render:** Compact alert cards with click-to-navigate functionality

### Vehicle List (`src/app/client/vehicles/page.tsx`)

**Dynamic Status Update Logic:**
```typescript
// For each vehicle:
vehiclePredictions = allPredictions.filter(p => p.device_id === vehicle.deviceId)
hasCritical = vehiclePredictions.some(p => p.severity === 'CRITICAL')
hasHigh = vehiclePredictions.some(p => p.severity === 'HIGH')
hasWarning = vehiclePredictions.some(p => p.severity === 'WARNING')

// Status cascade (priority order):
if (hasCritical) status = 'Critical'
else if (hasHigh) status = 'Warning'  
else if (hasWarning) status = 'Service Due'
else status = 'Healthy'
```

### Vehicle Detail Page (`src/app/client/vehicles/[id]/page.tsx`)

**Issue Translation Algorithm** (`generateIssueMessages()`)
- Converts ML model issue codes into human-readable diagnostic messages
- Logic branches:
  1. **Threshold violations:** 
     - Parse sensor name from `THRESHOLD_sensorName`
     - Check if `minValue < threshold.min` or `maxValue > threshold.max`
     - Generate message: "Coolant Temp dropped to 23°C (Below safe minimum of 70°C)"
  2. **RoC anomalies:** "Rapid Engine RPM fluctuation detected"
  3. **Pattern anomalies:** Predefined explanatory messages for each pattern type

**Alert Display Logic:**
- Filters predictions for current vehicle's deviceId
- Groups by severity (CRITICAL/HIGH displayed prominently)
- Shows sensor snapshots with threshold context
- Displays min/max values from alert window for diagnosis

## Key Algorithms Summary

### 1. **Severity Ranking System**
```python
severity_rank = {'INFO': 0, 'WARNING': 1, 'HIGH': 2, 'CRITICAL': 3}
```
Used for alert escalation and comparison

### 2. **Time-Window Clustering**
- Groups anomalies occurring within 120 seconds
- Updates existing window if within time delta: `(current_timestamp - window_start).total_seconds() <= 120`
- Closes window and creates new one if time delta exceeded
- Tracks aggregate statistics across window (min/max values, anomaly count)

### 3. **Multi-Criteria Filtering**
- Dashboard: Severity filter → Time sort → Limit
- Vehicles: Device ID join → Severity aggregation → Status cascade

### 4. **DeviceID-to-Vehicle Mapping**
- Frontend vehicles store `deviceId` integer
- ML predictions use `device_id` integer  
- Join operation: `predictions.filter(p => p.device_id === vehicle.deviceId)`
- Enables one-to-many relationship (one vehicle → multiple predictions over time)

## Data Flow Pipeline

```
1. Vehicle Sensors → Raw Telemetry Data (CSV/DataFrame)
2. Python ML Agent → Processes with 3-tier detection → Generates alerts
3. Alert Aggregation → Time-windowed clustering → JSON output file
4. Next.js API Route → Reads JSON → Serves via REST endpoint
5. React Components → Fetch predictions → Join with vehicle data
6. State Management → Filter/sort/aggregate → Update UI
7. User Interaction → Click alert → Navigate to detail view with full diagnostic data
```

---

## Critical Integration Points

1. **deviceId Consistency:** Frontend vehicle.deviceId MUST match ML model device_id
2. **Severity Enum:** Both systems use identical severity levels: INFO, WARNING, HIGH, CRITICAL
3. **Sensor Field Names:** ML model output sensor names must match frontend threshold object keys (cTemp, rpm, speed, battery, eLoad, maf)
4. **Timestamp Format:** ISO 8601 strings for start_time/end_time enabling JavaScript Date parsing
5. **Issue Code Convention:** Structured as `TYPE_DETAIL` (e.g., THRESHOLD_cTemp, PATTERN_ALTERNATOR) for frontend parsing
